# План апгрейда `time_filter` до нескольких окон

## 1. Цель и область изменений

Расширить `trade_filter.time_filter`, добавив несколько разрешённых внутридневных интервалов с сохранением старого `window`.

Изменение должно одинаково работать в:

- WF-оптимизации через `config.yaml`;
- одиночном tester;
- batch tester через `config_tester.yaml`;
- ZigZag/FSM runtime;
- standalone-volume runtime.

Парсинг, валидация, нормализация и построение временных масок должны быть общими. Отдельной бизнес-логики для WF и tester создавать не нужно.

## 2. Формат конфигурации

Новый формат:

```yaml
trade_filter:
  time_filter:
    enabled: true
    windows:
      - "09:00-12:00"
      - "16:00-18:00"
```

Старый формат остаётся полностью поддержан:

```yaml
trade_filter:
  time_filter:
    enabled: true
    window: "09:00-19:00"
```

### Правила совместимости

- Разрешён ровно один из ключей: `window` или `windows`.
- Одновременное присутствие обоих ключей запрещено независимо от `enabled`.
- При `enabled: true` один из них обязателен.
- При `enabled: false` отсутствие обоих полей допустимо.
- Старый `window` внутри runtime нормализуется в список из одного интервала.
- После нормализации runtime не должен различать старый и новый формат.

## 3. Семантика интервалов

Каждый интервал является полуоткрытым:

```text
[start, end)
```

Для конфигурации:

```yaml
windows:
  - "09:00-12:00"
  - "16:00-18:00"
```

получаем:

```text
[09:00, 12:00)
[16:00, 18:00)
```

На плотных минутных данных:

- `09:00–11:59` — входы разрешены;
- `12:00–15:59` — входы запрещены;
- `16:00–17:59` — входы разрешены;
- начиная с `18:00` — входы запрещены.

Секунды и более мелкие единицы времени, как и сейчас, игнорируются. Например:

- `11:59:59` относится к минуте `11:59` и находится внутри окна;
- `12:00:30` относится к минуте `12:00` и находится вне окна.

Временная зона берётся непосредственно из индекса данных. `time_filter` не выполняет преобразование UTC/local time и DST-коррекцию.

## 4. Пересечения, сортировка и соприкасающиеся интервалы

`windows` автоматически сортируется по времени начала во внутреннем нормализованном представлении. Исходный порядок YAML не должен влиять на результат.

Запрещены:

- дубли;
- интервалы с `start >= end`;
- cross-midnight интервалы;
- пересечения;
- полное вложение одного интервала в другой;
- соприкасающиеся интервалы, например `[09:00,12:00)` и `[12:00,18:00)`.

Соприкасающиеся интервалы запрещаются потому, что между ними нет перехода `inside → outside`, а значит невозможно одновременно трактовать их как два отдельных цикла с обязательным reset на общей границе.

Если требуется непрерывное окно, оно должно быть записано одним интервалом:

```yaml
windows:
  - "09:00-18:00"
```

После сортировки для каждой соседней пары должно выполняться:

```text
previous.end < next.start
```

## 5. Валидация

### Структурная валидация

Выполняется независимо от `enabled`:

- `time_filter` должен быть mapping;
- неизвестные ключи запрещены;
- `enabled` должен быть `bool`, если указан;
- одновременное присутствие `window` и `windows` запрещено.

### Глубокая валидация

Выполняется при `trade_filter.enabled=true` и `time_filter.enabled=true`.

Для `window`:

- значение должно быть строкой;
- формат строго `HH:MM-HH:MM`;
- часы `00–23`;
- минуты `00–59`;
- начало строго раньше конца;
- cross-midnight запрещён.

Для `windows`:

- значение должно быть списком;
- список должен быть непустым;
- каждый элемент должен быть строкой;
- каждый элемент должен соответствовать `HH:MM-HH:MM`;
- каждый интервал должен иметь `start < end`;
- дубли запрещены;
- пересечения запрещены;
- соприкасающиеся интервалы запрещены;
- порядок входного списка произвольный — resolver сортирует автоматически.

При `time_filter.enabled=false` сохраняется старое поведение: содержимое `window`/`windows` хранится, но не проходит глубокую проверку диапазонов. При последующем включении фильтра оно будет провалидировано.

Для новых ошибок должны быть введены стабильные error keys, как минимум:

```text
time_filter_window_and_windows_conflict
time_filter_windows_missing
time_filter_windows_invalid_type
time_filter_windows_empty
time_filter_windows_item_invalid_type
time_filter_windows_item_invalid_format
time_filter_windows_item_invalid_hours
time_filter_windows_item_invalid_minutes
time_filter_windows_item_zero_length
time_filter_windows_item_cross_midnight
time_filter_windows_duplicate
time_filter_windows_overlap
time_filter_windows_touching
```

Старые error keys для `window` сохраняются без переименования.

## 6. Внутреннее представление

`TradeFilterTimeFilterConfig` расширяется полем:

```python
windows: Optional[list[str]]
```

После валидации resolver строит одно каноническое внутреннее представление, например:

```python
_windows_minutes: tuple[tuple[int, int], ...]
```

где каждый элемент содержит:

```text
(start_minute_of_day, end_minute_of_day)
```

Примеры:

```text
"09:00-12:00" → (540, 720)
"16:00-18:00" → (960, 1080)
```

Для старого:

```yaml
window: "09:00-19:00"
```

результат:

```python
_windows_minutes = ((540, 1140),)
```

Runtime должен читать только каноническое представление. Старые `_start_hour`, `_start_minute`, `_end_hour`, `_end_minute` можно временно сохранять для совместимости с существующими test doubles, но они не должны оставаться основным runtime-контрактом.

## 7. Runtime-маска

Общая разрешающая маска:

```text
in_window[t] =
    in_window_1[t]
    OR in_window_2[t]
    OR ...
```

Для каждого интервала:

```text
in_window_i[t] =
    start_i <= minute_of_day[t] < end_i
```

При выключенном фильтре:

```text
in_window = all True
reset_event = all False
```

## 8. Reset-события

### Основное правило

На плотных данных reset формируется на первом реально существующем баре вне завершившегося разрешённого интервала:

```text
reset_event[t] =
    in_window[t-1]
    AND NOT in_window[t]
```

Для заданных минутных окон это даёт reset в `12:00` и `18:00`.

### Защита от пропущенных баров

Одного сравнения объединённой маски недостаточно. Если данные переходят напрямую:

```text
11:59 → 16:00
```

получается `True → True`, хотя граница `12:00` была пересечена.

Поэтому helper дополнительно должен обнаруживать пересечение конца интервала между соседними timestamp. Если предыдущий наблюдаемый бар находился внутри интервала, а следующий timestamp уже находится после его конца, reset ставится на первый следующий реально существующий бар.

Пример:

```text
11:59 → 16:00
```

Результат:

```text
time_filter_in_window[16:00] = 1
time_filter_reset_event[16:00] = 1
```

На этом баре reset имеет приоритет, поэтому новый вход в `16:00` не выполняется. Новый цикл сможет открыть позицию начиная со следующего бара.

Это fail-closed поведение: при неполных данных важнее гарантированно не переносить позицию/FSM между циклами, чем разрешить вход на первом баре нового окна.

Аналогичное правило применяется при переходе:

```text
17:59 текущего дня → 09:00 следующего дня
```

Reset ставится на `09:00`, если после предыдущего разрешённого бара отсутствовали строки вне окна.

Один булевый элемент маски представляет одно или несколько пропущенных окончаний интервалов. Счётчик reset отражает фактически материализованные reset-бары, а не число календарных границ без строк данных.

### Первый бар ряда или WF-среза

На первом баре ряда:

```text
reset_event[0] = False
```

даже если он находится вне окна.

Каждый отдельный backtest/WF-срез начинает runtime с чистого состояния и без открытой позиции. Поэтому синтетический reset на первом баре не требуется.

Документацию нужно привести в соответствие с этим правилом, поскольку текущая спецификация и текущие тесты расходятся.

## 9. Семантика принудительного закрытия

Сохраняется действующая open-to-open модель:

```text
решение на close(t)
исполнение на open(t+1)
```

Если reset сформирован на баре `12:00`, то:

- на `12:00` сбрасываются FSM, lifecycle и candidate state;
- формируется сигнал закрытия;
- `positions[t+1] = 0`;
- фактическое нулевое состояние позиции появляется на следующем баре;
- сделка получает `exit_reason="filter_time_reset"`.

Следовательно, термин «закрытие в 12:00» в документации означает «сигнал принудительного закрытия на баре 12:00 по текущей open-to-open модели», а не исполнение на open 12:00.

Менять общую модель исполнения в рамках этого апгрейда запрещено.

## 10. Сброс состояния

Каждый `time_filter_reset_event` должен повторять существующий полный reset:

- FSM переходит в `OFF`;
- lifecycle counters сбрасываются;
- `held_pos` сбрасывается;
- cycle direction и cycle counters сбрасываются;
- ZigZag candidate state получает `combined_reset_event`;
- wakeup state сбрасывается;
- позиция закрывается по open-to-open правилам;
- новый вход на reset-баре запрещён.

Общая маска:

```text
combined_reset_event =
    daily_reset_event OR time_filter_reset_event
```

При совпадении событий сохраняется приоритет:

```text
daily_reset > time_filter_reset
```

Обновить оба runtime caller:

- ZigZag/FSM;
- standalone volume.

В `zigzag_st_filter.apply()` устранить существующий повторный расчёт reset-масок после `_resolve_apply_reset_events`. Внутри `apply()` должен быть один источник:

```python
reset_events = _resolve_apply_reset_events(...)
```

и далее только использование полученных массивов.

Test override:

```python
time_filter_events=(in_window, reset_event)
```

сохраняется без изменения контракта.

## 12. Диагностика

Сохраняются существующие поля и dtype:

```text
time_filter_enabled
time_filter_in_window
time_filter_reset_event
```

Значения:

- `time_filter_in_window=1` внутри любого разрешённого интервала;
- `time_filter_in_window=0` вне всех интервалов;
- `time_filter_reset_event=1` на материализованном reset-баре.

Причины должны различаться по уровням:

- reset-бар:
  ```text
  filter_block_reason = time_filter_reset
  ```
- последующий запрещённый вход между окнами:
  ```text
  filter_block_reason = time_filter_out_of_window
  ```
- trade-level выход:
  ```text
  exit_reason = filter_time_reset
  ```

При совпадении с daily reset:

```text
filter_block_reason = daily_reset
exit_reason = filter_daily_reset
```

Summary-счётчики сохраняются:

```text
time_filter_reset_count
time_filter_bars_in_window
time_filter_bars_out_window
time_filter_enabled
```

## 13. Тесты конфигурации

Для обоих loader-контуров проверить:

- старый `window` загружается без изменений;
- новый `windows` загружается;
- `window` нормализуется в один интервал;
- `windows` сортируется автоматически;
- `window + windows` отклоняются;
- при `enabled=true` отсутствие обоих полей отклоняется;
- пустой список отклоняется;
- scalar, mapping и `null` вместо списка отклоняются;
- нестроковый элемент отклоняется;
- неверный формат отклоняется;
- неверные часы и минуты отклоняются;
- `start == end` отклоняется;
- `start > end` отклоняется;
- дубликаты отклоняются;
- частичное пересечение отклоняется;
- полное вложение отклоняется;
- соприкасающиеся интервалы отклоняются;
- при `enabled=false` сохраняется старое отсутствие глубокой валидации;
- неизвестные ключи отклоняются.

## 14. Тесты runtime-маски

Для плотного минутного индекса проверить:

- `08:59` — запрещено;
- `09:00` — разрешено;
- `11:59` — разрешено;
- `12:00` — запрещено и reset;
- `12:01–15:59` — запрещено без повторных reset;
- `16:00` — разрешено;
- `17:59` — разрешено;
- `18:00` — запрещено и reset;
- после `18:00` — запрещено без повторных reset.

Дополнительно:

- секунды игнорируются;
- tz-naive и tz-aware индекс используют локальные компоненты индекса;
- non-DatetimeIndex отклоняется;
- non-monotonic индекс отклоняется;
- несовпадение длины индекса отклоняется;
- disabled filter возвращает all-ones/all-zeros.

## 15. Тесты пропусков данных

Обязательно проверить:

```text
11:59 → 12:01
```

Reset возникает на `12:01`.

Проверить:

```text
11:59 → 16:00
```

На `16:00` одновременно:

```text
in_window = 1
reset_event = 1
```

Reset имеет приоритет, новый вход на этом баре запрещён.

Проверить:

```text
17:59 текущего дня → 09:00 следующего дня
```

Reset возникает на `09:00`.

Проверить, что первый бар отдельного ряда или WF-среза никогда не получает синтетический reset.

## 16. Поведенческие и интеграционные тесты

Проверить для ZigZag/FSM и standalone volume:

- позиция закрывается после каждого reset по схеме `t → t+1`;
- FSM и lifecycle полностью сбрасываются;
- candidate state сбрасывается;
- между окнами новые входы запрещены;
- в новом окне начинается новый цикл;
